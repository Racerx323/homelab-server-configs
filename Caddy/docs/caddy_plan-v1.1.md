## Locked Decisions

- Deployment will proceed one authorized and validated action at a time.
- The living plan remains at `Caddy/docs/caddy_plan-v1.1.md`.
- Repository tooling is idempotent and supports dry-run, rollback, and uninstall.
- TLS secrets are sourced from Doppler project `homelab-dev`, config `prd_caddy`.
- Doppler is installed and used only on the Ubuntu operator workstation; neither
  Caddy node receives the Doppler package or credentials.
- Caddy serves HTTP/1.1, HTTP/2, and HTTP/3; firewall intent includes UDP 443.
- Runtime services and scripts log only through systemd-journald.
- Node-specific Pi-hole names remain available in addition to the shared HA name.
- UniFi read-only collection uses local API key name `audit` with Doppler
  reference `homelab-dev/prd_unifi:AUDIT`; the key value is never recorded.
- Caddy client access is limited to Default LAN VLAN 1; IoT VLAN 200 and Guest
  VLAN 400 are excluded.
- lighttpd is installed and managed as a Pi-hole artifact. Caddy deployment
  must not replace or independently manage the package, must preserve the
  current Pi-hole PHP/FastCGI tree, and must revalidate/regenerate its derived
  loopback candidate after Pi-hole upgrades.
- Material security, network, interface, behavior, scope, or ownership deviations
  require approval; minor mechanical deviations are recorded with rationale.

### Bidirectional lsyncd and atomic reloads

Configure reciprocal streams:

- Node A outbound releases → Node B incoming/A.
- Node B outbound releases → Node A incoming/B.

Synchronize immutable, revisioned releases rather than live `/etc/caddy` files. Each release contains:

- Caddy configuration.
- Certificate files.
- Manifest and content hashes.
- Parent revision.
- Source node.
- Completion marker.

Disable remote deletion and exclude editor files, temporary files, runtime state, logs, and incomplete releases.

Node A is the normal writer. Node B publishing is allowed only when:

- Its Caddy VRRP group is MASTER.
- Emergency mode is explicitly supplied.
- Its parent revision matches the active revision.

Quarantine divergent or concurrent revisions and notify the operator instead of resolving conflicts through timestamps.

The reconciler verifies release completeness, hashes, revision ancestry, certificate/key pairing, certificate chain, and Caddy configuration before atomically changing `/etc/caddy/current`.

11. Fail Caddy on A, verify both VIPs move to B, and test guarded B→A emergency publishing.
12. Test invalid-release quarantine, interrupted rsync recovery, revision conflicts, and peer reconnection.
13. Confirm Apprise receives notifications through `/notify/apprise`.
14. Test IPv4-only, IPv6-only, iOS Safari, and Android Chrome clients.
15. Perform failback, rolling-upgrade, and rollback drills.
16. Record actual versions, paths, checksums, failover timing, and deviations for documentation.

Acceptance requires:

- Exactly one owner for both Caddy VIPs.
- Successful trusted TLS from desktop and mobile clients.
- Continued Pi-hole admin access after failover.
- Working reciprocal synchronization without silent conflicts.
- Working Munin metrics and Apprise notifications.
- No external-zone reachability.
- No regression to the existing DNS VIP cluster.

## Post-Deployment Documentation and Reliability

Only after acceptance, create:

- `Caddy/README.md`
- `Caddy/docs/QUICK_START.md`
- `Caddy/docs/INSTALLATION.md`
- `Caddy/docs/UNINSTALLATION.md`
- `Caddy/docs/TROUBLESHOOTING.md`
- Mermaid architecture and failover diagram
- LikeC4 source/view documentation and generated-view provenance

Reliability defaults:

- Retain the last ten validated releases per node.
- Alert at 30, 14, and 7 days before certificate expiry.
- Renew certificates through staged releases; never overwrite live files.
- Upgrade Node B first, fail over intentionally, then upgrade Node A.
- Run quarterly IPv4/IPv6 failover and mobile TLS tests.
- Keep lsyncd outside the VRRP health dependency.
- Keep Caddy administration and metrics loopback-only.
- Preserve the existing DNS VRRP group independently so reverse-proxy problems cannot remove DNS service.
- Treat automated DNS-challenge renewal as a future enhancement.
